スライド 09　Astro v1
目安時間：1 分 15 秒（04:15〜05:30）

話す文章
Astro v0.21 で Go Compiler と Vite を採用しました。この図は、その後の 2022 年の Astro v1 です。
Go を選んだ理由について、実装した Nate Moore は、esbuild が Go だったことと、Go が学びやすかったことを挙げています。将来のすべてを予測して決めたというより、当時の実装を進めやすい選択でした。
JavaScript から Compiler を呼ぶ際には WASM を使います。WASM は WebAssembly の略で、対応する実行環境で動かせるバイナリ形式です。
図の Compiler は、.astro を TypeScript を含むコードへ変換します。そのコードを Vite の連携機能が esbuild で JavaScript に変換します。
Compiler の箱の中にも esbuild がありますが、こちらは CSS の解析と生成を担当します。さらに HTML5 Parser を基に、Astro の構文を解析しています。この時点では、サイトを Build するための変換が中心でした。

補足
HTML5 Parser は、HTML の文法や親子関係を解析する実装です。Go Compiler は HTML5 Parser 由来の実装を Astro syntax に対応するよう拡張しています。
Compiler 内の CSS Parser と Printer は esbuild 由来で、2022 年 3 月の PR #329 で導入されました。CSS の解析とスコープ化を担います。スコープ化は、スタイルが対象のコンポーネントに適用されるよう selector などを変換することです。
図の Vite に付いた esbuild は TypeScript の変換を担当します。Compiler 内の CSS の機能とは役割が異なります。

スライド 14　Astro Syntax
目安時間：1 分 00 秒（08:30〜09:30）

話す文章
初期表示
左は、表のセルに foo という式があり、表の後に h2 があるコードです。h2 は table の外に書いてあります。

クリック 1
ところが、当時報告された生成 HTML では、右のように h2 が table の中に入っていました。書いた親子関係と生成結果が異なります。

クリック 2
この例では、Astro の構文をどう解析していたかを確認する必要があります。

クリック 3
Go Compiler は HTML5 Parser を拡張して使っていました。表の中の式を解析した後、周囲の HTML に合う解析状態へ戻せなかったことが原因です。
これは Compiler の不具合です。ブラウザが HTML の規則に従って行う補正とは区別します。Compiler が生成する HTML と、ブラウザが表示のために作る DOM という木は、別々の段階で作られます。

補足
compiler#870 と修正 PR #925 の例です。PR は表の式を特別扱いする分岐を削除し、式の終了時に resetInsertionMode() で解析状態を選び直します。表の後の要素が表に含まれないことも検査しています。
HTML correction は、HTML の規則によるタグの補完や親子関係の補正です。たとえば p の中に div を書くと、div の開始で p が閉じられます。補正した木だけでは、書かれていた入れ子をそのまま診断できません。
この不具合で生成された HTML を、HTML5 の正しい補正結果として説明しません。

スライド 17　Linter が .astro を検査するまで
目安時間：55 秒（10:15〜11:10）

話す文章

スライド 34　Lossless CST は何を保持するのか
目安時間：50 秒（22:20〜23:10）

話す文章
CST は Concrete Syntax Tree、具象構文木です。変数名や演算子に加え、セミコロンなどの記号も表します。Lossless は、元のコードを一文字も変えずに再現できる、という性質です。

補足

クリック 1

スライド 52　Sätteri と plugin の関連図
目安時間：1 分 00 秒（34:20〜35:20）

話す文章
図の上が JavaScript、下が Rust です。JavaScript の satteri は公開 API と plugin の登録を提供し、Node-API bindings を介して Rust の satteri を呼びます。
Rust は解析器、AST、MDX の変換を担う部品を組み合わせます。MDAST は Markdown を表す AST、HAST は HTML を表す AST です。
右上の JavaScript plugin は、対象の node に対して visitor を実行します。visitor は、該当する種類の node を調べる関数です。変更したい場合は、ctx という操作の入口から、プロパティの変更や node の交換を指定します。
往復する線は、node の情報を渡し、変更内容を返す関係です。Rust に解析や変換を任せながら、JavaScript で拡張できる API を用意しています。

補足
図の pulldown-cmark は satteri-pulldown-cmark、mdxjs-rs は satteri-mdxjs-rs の略記です。前者は MDX に対応した Parser、後者は Oxc を利用する MDX Compiler です。satteri-ast が MDAST と HAST を担い、関連部品に satteri-arena と satteri-plugin-api もあります。
図は主な依存関係で、すべての入力が同じ経路をたどるという意味ではありません。
node のプロパティは直接変更せず、ctx の setProperty() や replaceNode() などで変更を指定します。visitor の完了後に適用されます。visitor の戻り値で node を交換する方法もあります。
この API は remark と rehype の plugin API と同一ではありません。既存 plugin との互換性は次のページで説明します。
